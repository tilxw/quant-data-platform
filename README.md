# A 股金融数据平台

一条端到端的离线数据链路：**采集 → 入库 → 质检 → 指标加工 → 回测应用**。
存储采用 DuckDB（列式、单文件、完整 SQL）；增量采集 + 幂等写入保证不重不漏，
质检作为闸门把关数据质量；下游回测引擎自研，并与 `vectorbt` 及一个独立参考实现
做**三方对拍**验证正确性。cron 每个工作日自动触发整条链路。

```
akshare 行情(新浪) ─┐
                    ├─→ DuckDB ─→ 质检 ─→ 因子 ─→ 向量化回测 ─→ 报告
自写爬虫(龙虎榜)   ─┘   (7表)    (闸门)   (5个)    (三方对拍)

cron 定时触发 → run_pipeline.py 按依赖编排上述各步，质检报 ERROR 则下游不跑
```

| 数据 | 规模 | 区间 |
|---|---|---|
| 日线行情 + 复权因子 | 各 339,512 行（新浪） | 2022-01-04 → 2026-09-30 |
| 龙虎榜（自写爬虫） | 86,473 行 / 1150 个交易日无缺口 | 同上 |
| 因子值 | 1,660,360 行（5 因子 × 300 只） | 同上 |
| 全库合计 | 2,435,648 行（7 张表） | — |
| 单元测试 | 95 个 | — |

> 规模为 2026-09-30 的快照；此后由 cron 每个工作日增量更新。

## 设计要点

**存储：原始价 + 复权因子分表**
行情表存交易所真实价（不复权），复权因子单独一表，前/后复权价用时现算。
复权价会随分红修正而过时，存它等于改写历史；原始价是事实、永不需修改，
且计算市值与判断涨跌停必须用它。一份数据支持三种口径。

**采集：增量更新 + 幂等写入**
复合主键 `(symbol, trade_date)` + `INSERT OR IGNORE`，任意时刻重跑不产生重复行；
增量起点取库内该股最后一日的次日，已最新则一个请求都不发。
日线只采到 T-1——盘中数据不完整，而幂等写入不覆盖已入库的行，半根 K 线一旦
入库就永远不会被修正。

**异常分档**：核心数据（交易日历/成分股名单）失败 → 直接停；单只/单日失败 →
记录并跳过；网络抖动 → 指数退避重试；失败比例超阈值 → 熔断（失败数一超阈值
立即停止，不再把剩余标的试完——2026-10 东财断连时实测，请求数从约 900 降到 93）。
实测 1103 个交易日回溯中 21 次超时抖动经重试挽救 20 次。

**自写爬虫（龙虎榜）**：F12 定位东方财富 JSONP 接口（以 `<script>` 加载，
不在 XHR 筛选中；去掉 `callback` 参数即得纯 JSON）。requests 骨架带 UA/Referer
防盗链、连接与读取分离超时、指数退避重试、自动翻页；区分上游"业务空数据码"
与真实故障。主键含**上榜原因**——同一只股票同一天可因多个原因分别上榜。

## 数据质检

| 检查 | 对照基准 | 抓什么 |
|---|---|---|
| 新鲜度 | 交易日历上最近一个已收盘交易日 | 采集断更 |
| 完整性 | 日历 ∩ [该股首条行情日, 最新日] | 漏采（上市前日期已排除） |
| 因子体检 | 复权因子只随分红上行；后复权日收益不超涨跌停 | 因子错误（回撤 >0.5% 或收益超 ±21% 即 ERROR） |
| 跨源对拍 | 独立且**同流派**的第二数据源 | 单一数据源的系统性错误（日常流水线暂停，见下） |

对拍口径比**日收益率**而非价格：两源后复权锚点不同，价格天然差一个乘法常数，
在收益率的除法中自动消掉。实测据此识别出某数据源采用"加法复权"流派、
日收益率被系统性压缩，将其排除出对拍源。

因子回撤与超限收益原为 WARN，2026-10 改判 ERROR：复权因子绝不会下降，舍入噪声
至多约 0.25%，超过 0.5% 的回撤只能是数据错误。改判前在两个库上验证——新浪全量库
33.9 万行 0 次触发；已知有错的东财存档库 6 只问题股全部拦下（均经分红公告证实）。

**跨源对拍暂停**：主行情源换成新浪后，唯一的独立源东财既对连续请求断连、7 月下旬起
返回的复权数据也有误，拿它当闸门参照会把正常的流水线误拦。日常流水线以
`--skip-cross` 运行，需要时可手动指定对拍源。

结果双写 Markdown 体检单与 `qc_result` 表；存在 ERROR 时以非零退出码返回，
由编排器消费：质检不过，因子与回测不跑。

## 调度

`scripts/run_pipeline.py` 按依赖串行编排：行情 → 质检（闸门）→ 龙虎榜 → 因子 → 回测。
质检是**控制依赖**——因子不读质检表，但必须等它放行。

- 每步以子进程运行，只认退出码 0 / 非 0：查出数据问题与脚本崩溃都要停，区分不改变动作
- 任一步非 0 即告警（附该步日志最后 20 行）并跳过下游；每步 1 小时超时，防卡死
- 编排层不重试：采集内层已做请求级重试与熔断，外层再试只会放大请求；每步幂等，失败修好后整条重跑即可
- 触发用 cron（工作日一次）；5 个脚本、单机、一天一次，不值得为它运维一套 Airflow。
  编排按 Airflow 概念写成（步骤 ↔ Task，步骤列表 ↔ DAG，非 0 跳过下游 ↔ upstream_failed），迁移成本低

## 数据源迁移（2026-10：东财 → 新浪）

**起因**：东财行情接口对同一出口 IP 首个请求放行、后续连续请求直接断连（akshare 社区自
2026-02 起有同类报告），且 7 月下旬起返回的复权数据本身有误。

**做法**：不在原库上改，用**影子库**——
1. 新浪全量重灌一个新库（300 只、0 失败），原东财库原样保留
2. 新旧全量对账（`scripts/compare_sources.py`）：收盘价逐日全一致；后复权收益 294 只一致、6 只不一致
3. 用**巨潮分红公告**当第三方裁判（`scripts/verify_exdates.py`）：6 只共 38 次除权，新浪吻合 37 次、
   无法解释的因子跳变 0 次；东财无法解释的跳变 86 次
4. 切换：新库接管主库，东财库存档

**结论**：问题全在东财一侧——000001 的复权数据长期有误（质检里那条遗留 WARN 的根因），
另 5 只是东财 7 月下旬后新返回的数据有误。唯一未吻合的 1 次（000157，2023-07-21）两源结果一致、
仅与名义派息不符，疑为回购股份导致的虚拟分派，未查实。

## 因子

| 因子 | 定义 | 维度 |
|---|---|---|
| `mom20` | 后复权价过去 20 个交易日累计涨幅 | 趋势 |
| `vol20` | 日收益率的 20 日滚动标准差 | 风险 |
| `rev5` | 过去 5 日涨幅取负 | 短期均值回归 |
| `illiq20` | Amihud 非流动性：\|日收益率\| ÷ 成交额(亿元) 的 20 日均值 | 流动性 |
| `lhb_cnt60` | 过去 60 个交易日的龙虎榜上榜天数（自写爬虫采集） | 资金关注度 |

- **时点语义**：`factor_value` 中 `trade_date` 为 T 的值，是"用到 T 日收盘为止的数据"
  算出的，当日收盘后才可得。回测层统一 `shift(1)` 后用于决定 T+1 仓位——
  因子定义保持纯粹，滞后期成为回测的可调参数。
- **停牌处理**：滚动窗口按库内已有交易行滚动，不按日历补齐（不制造不存在的价格行）。
- 长表存储 `(symbol, trade_date, factor_name, value)`：新增因子只是多一种
  `factor_name`，表结构零改动。

## 回测与验证

自研多标的向量化引擎：周频调仓、持仓权重漂移建模、A股三项交易成本
（佣金 0.025% 双边 + 印花税 0.1% **仅卖出** + 滑点 0.05% 双边）。
防未来函数由引擎内统一 `shift(1)` 保证，并有"篡改未来价格、断言历史净值不变"
的单元测试锁定。

**三方对拍**——同一组持仓权重，比净值曲线：

| 费率 | 自研 vs 独立参考实现 | 自研 vs vectorbt |
|---|---|---|
| 0.000% | **2.87e-15**（机器精度） | 8.24e-06 |
| 0.075% | 1.34e-04 | 5.18e-04 |

零成本口径下自研引擎与逐日循环显式记账的参考实现一致到机器精度
（比 1e-8 的目标小六个数量级以上）；vectorbt 在同口径的 8e-6 偏差经三方比对定位在其一侧
（随调仓次数累积，每次约 3.5e-8）。含成本口径的 1e-4 量级分歧来自成本记账
约定不同（换手计量基准、费用是否侵蚀达成权重），已验证其随费率线性缩放、
费率归零则消失，属建模约定差异而非计算缺陷。

对拍过程中查出并修复两个真实缺陷：引擎中现金未计入权重分母，半仓被按满仓计算
（涨跌都被放大）；对拍代码对 vectorbt 净值做首日归一化，把已扣的建仓成本又加了回来。

## 已知局限

- **幸存者偏差**：股票池取当前沪深300成分名单，历史上被剔出指数的个股不在样本内，
  回测收益存在系统性高估。修正需要历史成分股快照（point-in-time 股票池），列为后续方向。
- 停牌股按最近可得价格持有，未模拟无法卖出的情形；无涨跌停撮合限制。
- 跨源对拍为抽样制（哨兵股 + 随机轮换），非全量覆盖；且目前缺少可靠的独立源，日常流水线暂停对拍。
- 采集截止日按自然日"昨天"计算：长假期间每次运行会对休市日空发一轮请求（已评估，影响小，未改）。
- 夏普比率取无风险利率为 0。

## 快速开始

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python scripts/init_db.py                 # 建库建表（幂等）
pytest                                    # 95 个单元测试

python scripts/update_data.py --limit 5   # 冒烟：只采成分股前 5 只
python scripts/update_data.py             # 全量增量更新（默认新浪源；幂等，可随时重跑）
python scripts/update_billboard.py        # 龙虎榜（自写爬虫）增量补齐
python scripts/compute_factors.py         # 计算五因子
python scripts/run_qc.py --skip-cross     # 数据质检（跨源对拍暂停期间加 --skip-cross，零网络请求）
python scripts/run_backtest.py            # 分层回测 + 三方对拍，输出报告到 reports/
python scripts/run_pipeline.py            # 每日流水线：以上各步按依赖编排，日志在 logs/
python scripts/compare_sources.py         # 数据源迁移对账（只读）
python scripts/verify_exdates.py          # 复权因子 vs 巨潮分红公告（只读）
```

## 技术选型

| 决策 | 选择 | 理由 |
|---|---|---|
| 存储 | DuckDB | 列式存储适合整列聚合的行情分析；单文件零部署；完整 SQL。数据量再大一个量级时，换成按日期分区的 Parquet + Spark（见后续方向） |
| 回测 | 自研 + vectorbt 对拍 | 自研掌握引擎细节（成本、漂移、时间线对齐）；与成熟库交叉验证保证正确性 |
| 数据 | akshare（新浪）为主 + 自写爬虫 | 行情走成熟库求稳；另类数据往往无现成库，自写可控重试与降级策略。2026-10 因东财断连且数据有误迁至新浪，迁移前全量对账并以分红公告核对 |
| 调度 | cron + 手写编排 | 一天一次、单机、5 个脚本；按 Airflow 概念编写，规模上来后迁移成本低 |

## 后续方向

- **恢复跨源对拍**：换一个同为乘法复权的独立数据源（如 baostock），恢复每日对拍。
- **完整性检查补盲区**：目前按"已有行情的股票"分组检查，一行都没采进来的股票看不见；
  改为以股票池为准左连接行情表。另接停复牌数据，把"停牌"和"漏采"分开。
- **告警外发**：告警目前只写日志；接入钉钉 / 邮件，发送失败只记日志，不影响流水线。
- **CI**：每次推送自动跑单元测试，不通过不合并。
- **修正幸存者偏差**：用拉链表记录历史成分股，回测按当时的成分股取样。
- **规模扩大后的迁移**：行情按交易日分区存为 Parquet，加工换成 Spark / Hive SQL；
  调度迁到 Airflow，每个脚本包成一个任务，依赖照搬现有顺序。
